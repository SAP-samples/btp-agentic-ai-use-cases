**All files created by this skill MUST be inside the current directory.**

### Asset Naming Rules

**All `metadata.name` fields (both solution and every asset) MUST match:**

- Regex: `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`
- Max length: 63 characters

**MCP Server asset naming (folder + `metadata.name`)**

For MCP Server assets, follow the naming convention `{domain}-{purpose}-mcp-server` (e.g., `sap-s4-cost-center-mcp-server`) (more details below).

The asset folder under `assets/` and the `metadata.name` inside its `asset.yaml` **must be identical**. Derive both deterministically as mentioned above:
- **`{domain}`**: read `target.ordId` from the translation file and take the namespace (everything before the first `:`). Replace any dots with dashes to keep the name filesystem-safe.
  Example: `sap.s4:apiResource:API_COSTCENTER_SRV:v1` -> `sap-s4`.
- **`{purpose}`**: use the `<api-folder>` name from `specification/<spec-folder>/mcps/<api-folder>/`. Strip a leading `api-` or `api_` prefix, lowercase, replace `_` with `-`.
  Example: `api-cost-center` -> `cost-center`.
- Final name: `sap-s4-cost-center-mcp-server`. The asset lives at `assets/sap-s4-cost-center-mcp-server/` and its `asset.yaml` has `metadata.name: sap-s4-cost-center-mcp-server`.

See this rule whenever MCP Server asset names are referenced.

### ORD ID Construction

BUILD-managed assets that publish / expose an ORD ID (i.e. in `provides.apis[].ordId` or `metadata.ordId`) **MUST** use this ORD ID pattern:

```plain
customer.build:apiResource:<solution-name>.<asset-name>:v<revision>
```

Following the rules below:

| Segment           | Rule                                                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `customer.build`  | Fixed namespace prefix for customer-created assets.                                                                     |
| `apiResource`     | Fixed ORD resource type.                                                                                                |
| `<solution-name>` | `metadata.name` from `solution.yaml`. Must not contain dots; underscores allowed, hyphens are preferred.                |
| `<asset-name>`    | `metadata.name` from the asset's `asset.yaml`. Must not contain dots; underscores allowed, hyphens are preferred. |
| `v1`              | Fixed at `v1` for MVP; never incremented by customer or platform.                                                       |

**Example:**

```plain
customer.build:apiResource:claims-automation-3f8a1.ai-assistant-agent:v1
```

**Cross-asset reference:**
When an asset references another asset, either within or outside the solution, the ORD ID must be used. The `requires` entry's `ordId` depends on what is being referenced:

**Scenario 1 — Agent requires an MCP server asset**

The agent's `asset.yaml` includes the MCP server's ORD ID (using `apiResource`) in its `requires` block:

```yaml
requires:
  - name: s4-dispute-mcp
    kind: mcp-server
    ordId: customer.build:apiResource:claims-automation-3f8a1.s4-dispute-mcp-server:v1
```

If the MCP Server asset is newly created, the ORD ID in the `requires` block must match the one generated in its `asset.yaml`. The MCP Server `asset.yaml` must also include a `requires` block referencing the target API's ORD ID (from the translation file) to ensure proper resolution of dependencies, e.g.:

```yaml
requires:
  - name: CE_COSTCENTER_0001
    kind: api
    ordId: sap.s4:apiResource:API_COSTCENTER_SRV:v1
```

**Scenario 2 — Another asset (e.g. a workflow) requires an agent asset**

An agent's `provides` section uses `customer.build:apiResource:...` (the standard ORD ID Construction format). However, when another asset needs to call that agent, it must use the **`agent`** resource type instead of `apiResource` in its `requires` block:

```yaml
requires:
  - name: ai-assistant-agent
    kind: agent
    ordId: customer.build:agent:claims-automation-3f8a1.ai-assistant-agent:v1
```

### Examples

#### Example 1: Simple Solution
```yaml
apiVersion: solution.sap/v1
kind: Solution
metadata:
  name: my-app-3f8a1
  version: "1.0.0"
assets:
  - ref: ./assets/frontend/asset.yaml
```

#### Example 2: New MCP Server Asset
```yaml
apiVersion: asset.sap/v1

kind: Asset
type: mcp-server

metadata:
  name: s4-dispute-mcp-server
  translation: mcp-translation/translation.json
  apiSpec: mcp-translation/api-spec.edmx
  version: "1.0.0"

provides:
  apis:
    - name: s4-dispute-mcp-server
      kind: mcp-server
      ordId: customer.build:apiResource:full-stack-app-7c2e4.s4-dispute-mcp-server:v1

requires:
  - name: CE_DISPUTE_0001
    kind: api
    ordId: sap.s4:apiResource:API_DISPUTE_SRV:v1
```

The MCP Server asset folder must **only** contain the following files:
```
assets/s4-dispute-mcp-server/
├── asset.yaml                # as above
└── mcp-translation/
    ├── api-spec.<extension>  # original API spec
    ├── translation.json      # Translation file (generated by mcp-translation-file skill)
    └── .tool-list.json       # Tool list file (generated by mcp-translation-file skill)
```

**File sources:**
- Translation files are generated by the `mcp-translation-file` skill.
- API Spec files are the original API specs (downloaded during API discovery phase) that were used as input to the `mcp-translation-file` skill. They are still needed to ensure we can (re)generate the MCP Server Card during deployment.
- The `asset.yaml` file is generated by this skill.

**MCP Server ORD ID Convention:**

For newly created MCP Server assets, use the ORD ID convention from the "ORD ID Construction" section.

Ensure that the ORD ID in the MCP Server asset's `asset.yaml` matches **exactly** the `ordId` used in any consuming agent's `requires` entry. Otherwise, the platform cannot resolve the dependency.

For existing MCP Servers registered in UMS, no MCP Server asset will be created as part of the solution. Reference the known ORD ID directly in the agent's `asset.yaml` as previously mentioned, and include `version` if it is available from `get_mcp` and recorded in `intent.md`.

### Best Practices

1. **Use environment variables** for configuration (UI/service assets only - see note 1 for agents):
   ```yaml
   env:
     PORT: "3000"
     LOG_LEVEL: info
   ```

2. **Required folder structure** - always use this layout:
  ```
  ./
  ├── solution.yaml             # refs ./assets/<asset-name>/asset.yaml
  └── assets/
      └── <asset-name>/
          ├── asset.yaml
          └── ...                 # any other asset files that are needed (e.g. Dockerfile, source code, xs-app.json, translation file, etc.).
  ```
  When applicable:
    - The `Dockerfile` MUST be co-located with `asset.yaml` (i.e. inside `assets/<asset-name>/`).
    - The `container.buildPath` in `asset.yaml` must be `.` (relative to asset.yaml location).

### Workflow

When user requests YAML creation:

1. All solution files (i.e. `solution.yaml` and `assets/` folder) **MUST** live inside the current working directory. Create the assets folder if it does not exist (`mkdir -p assets`).

   **Generate a UUID fragment** for the solution name before creating `solution.yaml`:
   ```
   node -e "process.stdout.write(require('crypto').randomBytes(3).toString('hex').slice(0,5))"
   ```
   Append the output to the solution name (e.g. `my-solution-3f8a1`). This ensures uniqueness across deployments. Users may rename it afterwards.

2. **Ask clarifying questions if unclear**:
   - What type of asset? (based on the asset typed available to you)
   - Single or multi-container? (not applicable for mcp-server)
   - What framework? (Next.js, Python, etc.) (not applicable for mcp-server)

3. **Read JSON schemas for validation rules** (do NOT write any YAML until every schema below is read into context):
   - **Read** `assets/solution-schema.json` — for `solution.yaml` structure.
   - **For each asset type `<asset-type>` in the solution, Read** `<skill:<asset-type>>/assets/<asset-type>.json` — for that asset's `asset.yaml` fields. Reading `solution-schema.json` does NOT satisfy this; each asset type needs its own schema read.
   - After reading, note required fields, patterns (e.g., DNS-compatible names), and enums.


4. **Create appropriate structure inside `assets/`**:
   - Use single-container for simple apps
   - Use multi-component for AppRouter patterns
   - For `mcp-server` assets: create only `asset.yaml` + copy files generated by the `mcp-translation-file` skill (as-is, do not modify their contents in any way); nothing else

5. **Handle MCP Server assets** - Skip this step if no `mcps/` subfolder exists under any `specification/*/`.
   - For each `specification/<spec-folder>/mcps/<api-folder>/` that exists:
      1. Derive `<mcp-server-asset-name>` following the "MCP Server asset naming" rules described in the "Asset Naming Rules" section.
      2. Create `assets/<mcp-server-asset-name>/mcp-translation/` folder.
      3. Copy all files from `specification/<spec-folder>/mcps/<api-folder>/` into `assets/<mcp-server-asset-name>/mcp-translation/` (ensure that all required files are copied over, i.e. Translation File, API Spec and Tools list; do not modify their contents in any way).
      4. Create `assets/<mcp-server-asset-name>/asset.yaml` per the `mcp-server.json` schema, with some guidelines below:
        - Set `metadata.name` to `<mcp-server-asset-name>`.
        - Set `metadata.translation` to `mcp-translation/translation.json`.
        - Set `metadata.apiSpec` to `mcp-translation/api-spec.<extension>` (where `<extension>` is the original API spec file extension, e.g., `.edmx`, `.json`, etc.).
        - Set `provides.apis[].name` to the same value as `metadata.name`.
        - Set `provides.apis[].ordId` to the generated ORD ID for this MCP Server asset (see "ORD ID Construction" section).
        - Set `requires` to include the target API's ORD ID (from the translation file) to ensure proper resolution of dependencies.
      5. Register it in `solution.yaml` under `assets`.
 
   - If the solution includes an agent asset that uses these MCP Server assets (or underlying APIs), add the MCP Server ORD IDs to the agent's `asset.yaml` under `requires` (see Examples 2 and 6).
   - Do NOT create a Dockerfile, source code, or server implementation for MCP Server assets.

5.5. **Handle n8n-workflow assets** - Skip this step if the solution contains no `n8nworkflow` assets.

   For each `n8nworkflow` asset, after the workflow `.n8n.json` file has been written, **MUST** run the following script to generate the top-level `workflow:` block and `provides.apis[]` entries — do not write ordIds manually:

   ```bash
   node skills/n8n-workflow/scripts/generate-workflow-asset.js assets/workflows/<workflow-name>/<workflow-name>.n8n.json <workflow-name> <solution-name>
   ```

   Example path: `assets/workflows/<workflow-name>/<workflow-name>.n8n.json`

   Paste the script output verbatim into `asset.yaml`. Fill in `description` for each `kind: rest` entry based on the workflow context. See the n8n-workflow execution skill for full details.

6. **Include all required fields**:
   - metadata.name (solution) - must match pattern `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`
   - type - must match available schemas
   - container OR components (not applicable for mcp-server assets)

7. **Add best practices**:
   - Resource limits and environment variables (UI/service assets only - omit for agent assets, see Best Practices)
   - Health probes

8. **Validate**:
   - Check YAML syntax
   - Verify all required fields present (per JSON schema)
   - Ensure paths are correct and all paths are relative to `solution.yaml`
   - Validate against patterns and constraints
